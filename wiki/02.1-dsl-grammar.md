# 2.1 — DSL Grammar Reference

## Relevant Source Files
- `src/core/dsl.ts`

## TL;DR

The formula DSL is a tiny s-expression language: identifiers, integer literals, `true`/`false`, and a fixed set of known functions (`and`, `or`, `not`, `add`, `implies`, `eq`, `ne`, `lt`, `le`, `gt`, `ge`, `is`). It exists so the LLM writes something constrained and parseable instead of free-form code — `parseExpr()` is the only way a string becomes an `Expr`, and an unknown function name or malformed call throws `DslError` immediately.

## Overview

`src/core/dsl.ts` is deliberately self-contained: no external parser library, hand-written tokenizer and recursive-descent parser, capped at `MAX_SOURCE_LEN = 2000` chars and `MAX_DEPTH = 32` nesting (`src/core/dsl.ts:19-20`) to bound what an LLM-generated formula can do to the parser. This page documents the grammar precisely because, per `CLAUDE.md`, this is the DSL string format both the LLM and any human reviewer must write in.

## Key Concepts

| Concept | Description | Source |
|---------|-------------|--------|
| `Expr` | The AST union: `bool`, `int`, `ref`, `is`, `not`, `and`/`or`/`add` (variadic), `implies`/`eq`/`ne`/`lt`/`le`/`gt`/`ge` (binary) | `src/core/dsl.ts:1-8` |
| `Token` | `ident` / `int` / `lparen` / `rparen` / `comma`, each with source `pos` for error messages | `src/core/dsl.ts:24` |
| `Scope` | Caller-supplied lookup (`sortOf`, `enumValues`) the typechecker uses to resolve identifiers | `src/core/dsl.ts:14-17` |
| `DslError` | The only error type thrown by tokenize/parse/typecheck | `src/core/dsl.ts:10` |

## Grammar (informal)

```
expr    := INT | IDENT | "true" | "false" | call
call    := IDENT "(" [expr ("," expr)*] ")"
```

- Bare `IDENT` with no following `(` is a variable reference (`{ op: 'ref', name }`).
- `is(varname, enumvalue)` is a hard-coded two-argument special form (`src/core/dsl.ts:109-115`), not a normal function call — both arguments must themselves be bare identifiers.
- `not(x)` — unary.
- `and(a, b, ...)`, `or(a, b, ...)`, `add(a, b, ...)` — variadic, minimum 2 args (`VARIADIC_MIN2`, `src/core/dsl.ts:50`).
- `implies(a, b)`, `eq(a, b)`, `ne(a, b)`, `lt(a, b)`, `le(a, b)`, `gt(a, b)`, `ge(a, b)` — exactly 2 args (`src/core/dsl.ts:52`).

Example, from `CLAUDE.md`: `and(covered_business, not(sell))`.

## How It Works

`parseExpr(src)` (`src/core/dsl.ts:148-152`) runs `tokenize()` then `new Parser(tokens).parseTop()`. The tokenizer uses one sticky regex (`/\s*([a-z][a-z0-9_]{0,47}|-?\d+|[(),])/y`, `src/core/dsl.ts:28`) advanced manually via `lastIndex`, so every token position is known for error reporting. The parser is a single recursive method, `parseExpr(depth)` (`src/core/dsl.ts:85-145`), that special-cases `is(...)` before falling through to the generic arity dispatch for the rest of `KNOWN_FNS`.

`typecheck(e, scope)` (`src/core/dsl.ts:214-277`) walks the `Expr` and enforces: `and`/`or`/`not`/`implies` operate on `bool`; `add`/comparisons operate on `int`; `eq`/`ne` require both sides to have the *same* resolved type; `is(name, value)` requires `name` to resolve to `'enum'` in `Scope` and `value` to be one of `scope.enumValues(name)`.

`refsOf(e)` (`src/core/dsl.ts:181-212`) recursively collects every identifier name referenced anywhere in an `Expr` — used by `validateFormalization`'s cycle check (see [02 — Legal IR & DSL](02-legal-ir-and-dsl.md#how-it-works)) and by `reconcile.ts`'s duplicate-detection.

## Gotchas & Conventions

> ⚠️ **Gotcha**: `is(x, y)` requires both `x` and `y` to be *identifier tokens*, not general expressions — `this.expect('ident')` twice (`src/core/dsl.ts:110-113`). Writing `is(x, "y")` or `is(x(), y)` fails to parse even though the grammar otherwise treats identifiers loosely elsewhere.

> 📌 **Convention**: adding a new DSL function means updating three sets in lock-step: `VARIADIC_MIN2`/`UNARY`/`BINARY` (`src/core/dsl.ts:50-52`), the `Expr` union (`src/core/dsl.ts:1-8`), and both `compile()` in `src/core/compile.ts` and `evalExpr()` in `src/core/explain-plain.ts` — all three switch over `Expr['op']` and TypeScript's exhaustiveness checking will fail to catch a missed case in `evalExpr` unless it also switches on the literal type.
